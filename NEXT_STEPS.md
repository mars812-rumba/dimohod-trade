  проходов стен/перекрытий и фланцев; 8 семейств и 104 SKU с ценами из подтвержденной таблицы.

  оцинкованное исполнение.

  прямому/угловому исполнению и диапазону размеров консоли.

  подтвержденному пределу `diameter_max_mm`; марка стали и утепление для консоли не угадываются.
  Телескопическая консоль без подтвержденного диапазона диаметра автоматически не подбирается.
- Для явно выбранных редактором совместимых семейств различие контура не блокирует переход,
  например `одноконтурный шибер → сэндвич-труба`; конкретный SKU по-прежнему сужается по
  совпадающим заполненным присоединительным параметрам.
- Номенклатура заглушек нормализована: одноконтурная заглушка исключается, а оба написания
  сэндвич-позиции объединяются в `Сэндвич-заглушка опорная`. В `Хомуты и крепеж` добавлена
  `Сэндвич-опорная площадка` с 36 SKU и ценами из строки `Площадка` листа `Фланцы`; площадка
  связана с универсальной консолью по наружному диаметру.
- Тройники с К/О нормализованы по подтвержденным углам: написания `45`/`45гр` и `90`/`90гр`
  объединяются в семейства `45°` и `90°` отдельно для одноконтурного и сэндвич-исполнения.
- Четверники с К/О `90`/`90гр` также объединяются в одно семейство `90°` отдельно для каждого
  контура; повторный импорт использует то же каноническое название.
- Строка прайса `Прочистка/юбка` разделена на два самостоятельных семейства с одинаковыми ценами
  отдельных изделий: `Прочистка` и `Декоративная юбка`, по 75 SKU в каждом. Повторный импорт
  сохраняет это разделение.
- Публичный каталог автоматически скрывает категории без активных семейств. Фильтр категории
  показывает компактные реальные комбинации внутренней трубы, внешней трубы и исполнения;
  контур и поля с единственным вариантом не занимают место. Старые SKU получают структурированные
  варианты внешней трубы из подтвержденного заголовка секции прайса. Толщины внутренней трубы
  `0,5 / 0,8 мм` выбираются компактными кнопками отдельно от марки стали. Бейджи показываются в
  левом нижнем углу активного большого фото и поверх фото товарных карточек каталога, не
  накладываясь на миниатюры галереи. На мобильной карточке сразу после галереи идет компактный
  блок выбора исполнения с ценой на первом месте; бейджи помещаются в одну строку, а секции
  выровнены с уменьшенными вертикальными интервалами. В карточке и категории параметры собраны
  в одинаковые пары: материал/диаметр, внутренняя сталь/толщина и наружный материал/наружная
  сталь. Материалы и толщины выбираются toggle-переключателями; фильтры сворачиваются по стрелке,
  а бейджи каталога выровнены до одинакового размера. Мобильные секции карточки выровнены по
  ширине страницы: номер расположен над заголовком, без бокового столбца и горизонтального сдвига.
  Панель исполнения не наследует старый внешний `padding`; строки фильтра категории имеют единую
  высоту, а выбранные toggle-сегменты отображаются оранжевыми с белым текстом.
  Внутренний мобильный отступ панели уменьшен до `8px`, названия параметров показаны полностью,
  а строка цены разделена на пояснение слева и крупную сумму справа.
  Выбор марки стали в карточке условный: для оцинкованного внутреннего или наружного контура
  соответствующее поле AISI скрывается и возвращается только при выборе нержавейки.
  Фильтры карточки и категории унифицированы: контролы `40px`, более заметные подписи `9–11px`,
  компактные интервалы `5px/12px`; остальные формы проекта не изменены.
  Для этой унификации не добавлялся общий компонент: каталог повторяет визуальные CSS-правила
  карточки, сохраняя отдельную поисковую логику и обычный регистр значений.
  В каталоге материалу отдано больше ширины, dropdown диаметра/стали сужены, между разными
  контролами установлен явный зазор `12px`.

## Главный следующий этап

Сначала докручиваем совместимость до первого рабочего подбора комплекта.

Цель: конфигуратор должен собрать минимальный безопасный BOM-комплект, а не просто показать
каталог.

Критерии законченного продуктового результата, статусы автоматического и проверенного расчёта,
объяснимость выбора и путь до PDF/проверки специалистом описаны в
`docs/PRODUCT_DIRECTION_9_OF_10.md`.

## Приоритет 1 — Compatibility MVP → первый комплект

Нужно расширить текущие правила до сценария “первый расчет комплекта”.

Сделать:

1. Описать зоны трассы как входные данные:
   - `appliance_connection`;
   - `indoor_warm`;
   - `wall_or_ceiling_pass`;
   - `attic_or_cold_zone`;
   - `outdoor`;
   - `termination`.
2. Добавить сценарии источника:
   - банная печь;
   - камин;
   - твердотопливный котел;
   - газовый котел.
3. Сделать первый endpoint расчета:

```text
POST /api/v1/configurator/projects
POST /api/v1/configurator/projects/{id}/calculate
```

4. Результат расчета должен возвращать:
   - список SKU/BOM;
   - количество;
   - цену;
   - предупреждения `info/warning/error`;
   - причины выбора элементов.
5. Правило улицы остается жестким:

```text
outdoor / attic / cold_zone => only contour = сэндвич
```

## Приоритет 2 — Variant SEO URLs

Делать после первого слоя правил/совместимости.

Целевой URL:

```text
/catalog/sendvich-truba/d115-200-l1000-aisi430-ins50
```

Почему после правил:

- variant URL должен вести на полноценную карточку с совместимостью;
- SEO-страница должна иметь корректные warning/info по варианту;
- canonical URL должен строиться из `Product.slug + SKU.slug`.

Сделать:

1. Route:

```text
apps/web/app/catalog/[productSlug]/[variantSlug]/page.tsx
```

2. Backend endpoint:

```text
GET /api/v1/products/{product_slug}/variants/{variant_slug}/detail
```

3. На старый URL:

```text
/product/{productSlug}
```

оставить legacy-страницу или redirect на дефолтный вариант.

4. При смене diameter/steel/length:
   - обновлять URL через Next.js routing;
   - не делать полный reload;
   - перезапрашивать только данные выбранного варианта.

## Приоритет 3 — Уточнение правил у дымоходчиков

Нужно получить от специалистов правила, которые нельзя безопасно угадать:

- допустимая длина одноконтурного стартового участка;
- где именно обязателен переход на сэндвич для банной печи;
- правила прохода деревянного перекрытия;
- сколько крепежа на метр вертикального участка;
- когда нужен тройник;
- когда нужна ревизия;
- когда нужен конденсатоотвод;
- как назначение `баня`/`камин` соотносится с уже подтвержденными правилами по топливу;
- когда режим конденсата можно определить автоматически, а когда нужно спрашивать пользователя.

Первый справочник AISI 430/304/321/316 уже подтвержден и внедрен для SKU труб и всех
сэндвич-элементов: топлива, режим
конденсата, классы `эконом/стандарт/премиум` и температуры. Толщина стали не меняет температурный
профиль; расчет срока службы не входит в текущую логику.

До уточнения такие пункты должны быть `warning` или ручная проверка, не автоматический выбор.

## Приоритет 4 — Карточка товара и варианты

Текущая карточка может получать очень много SKU, например `Сэндвич-труба` содержит `1584` SKU.
Старая отдельная demo-карточка `Сэндвич-труба 115/200...` исключена из активного каталога:
её два синтетических SKU отсутствуют в исходном JSON-прайсе и не смешиваются с реальными вариантами.

Первый UI/SEO-слой выполнен: выбор параметров заменил длинные карточки SKU, цена и артикул
меняются вместе с URL. Первый этап масштабирования API также выполнен:

- совместимость рассчитывается для выбранного SKU, а не для всего семейства;
- предварительная выборка кандидатов выполняется в SQL;
- добавлен `GET /api/v1/products/{slug}/compatible?sku=...`;
- совместимость при смене SKU загружается отдельно и кэшируется на клиенте;
- подготовлены частичные составные индексы PostgreSQL.

Осталось:

- не грузить все SKU сразу на frontend;
- endpoint для sibling variants/options;
- красивое отображение “цена от”.

## Приоритет 5 — Медиа и документы

После стабилизации Product/Variant:

- привязать фото/рендеры к logical Product;
- чертежи размеров — к Variant или группе вариантов;
- инструкции/пожарные документы — к Product/category/scenario;
- не дублировать медиа вручную для 6000+ SKU.

## Не делать сейчас

- Не начинать массовый новый импорт без Product → Variant логики.
- Не делать SEO-страницы вариантов до минимального слоя совместимости.
- Не угадывать технические параметры.
- Не подставлять “типовой” диаметр печи/котла без источника.
- Не плодить отдельные React-страницы под каждый SKU.
