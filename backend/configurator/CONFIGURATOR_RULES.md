# Dimohod Trade — правила конфигуратора и совместимости

Обновлено: 2026-07-20

Этот документ фиксирует базовую логику подбора комплекта дымохода до того, как каталог разрастется
до десятков тысяч SKU. HTML-прототип рядом:

- `backend/configurator/chimney-configurator-png.html`

## 1. Главный принцип

Конфигуратор не должен выбирать “похожий товар”. Он должен собирать безопасную систему по
структурированным полям:

- `diameter_mm`;
- `contour`;
- `insulation_mm`;
- `product_kind`;
- `steel_grade`;
- `wall_thickness_mm`;
- `outer_diameter_mm`;
- монтажные условия пользователя.

Нельзя завязывать правила на названия товаров. Название — для человека, поля — для логики.

## 2. Базовое правило улицы

По улице возможен только сэндвич.

Это правило жесткое:

```text
zone = outdoor => contour = сэндвич
```

Одноконтурные элементы допустимы только внутри теплого помещения и только там, где это разрешено
типом источника тепла и монтажной схемой.

## 3. Диаметр

`diameter_mm` — это внутренний рабочий диаметр дымового канала.

Правила:

- весь комплект должен сохранять один `diameter_mm`;
- нельзя автоматически уменьшать диаметр;
- переходники допускаются только как явный элемент правила;
- если у печи/камина/котла неизвестен диаметр патрубка — автоподбор запрещен, нужна ручная проверка.

Для сэндвича:

```text
diameter_mm = внутренний диаметр
outer_diameter_mm = наружный диаметр
insulation_mm = толщина изоляции
```

Пример:

```text
Ø100/200 => diameter_mm = 100, outer_diameter_mm = 200, insulation_mm = 50
```

## 4. Зоны дымохода

Минимальная модель трассы:

```text
appliance_connection  # подключение к печи/камину/котлу
indoor_warm           # теплое помещение
wall_or_ceiling_pass  # проход через стену/перекрытие
attic_or_cold_zone    # холодная зона / чердак
outdoor               # улица выше кровли / фасад
termination           # оголовок
```

Правила по зонам:

| Зона | Разрешенный контур |
|---|---|
| appliance_connection | чаще одноконтурный |
| indoor_warm | одноконтурный или сэндвич |
| wall_or_ceiling_pass | сэндвич + проходной узел |
| attic_or_cold_zone | сэндвич |
| outdoor | только сэндвич |
| termination | сэндвич-оголовок под тот же диаметр |

## 5. Переход одноконтурный → сэндвич

Если трасса начинается одноконтурным участком и дальше выходит в холодную зону или на улицу, нужен
переход на сэндвич.

Минимальное правило:

```text
если есть zone >= wall_or_ceiling_pass:
  добавить старт/переход на сэндвич перед проходом
```

Переход должен сохранять `diameter_mm`.

## 6. Что уже есть в БД

На 2026-07-20:

- импортированы одноконтурные элементы из листа `голые`;
- импортированы сэндвич-элементы 50 мм из `prices/50mm.json`;
- текущие импортированные позиции переведены в модель `Product → Variant/SKU`;
- активных logical products: `40`;
- импортированных SKU с variant-полями: `6339`;
- одноконтурные SKU имеют `contour = одностенный`;
- сэндвич 50 мм имеет `contour = сэндвич`, `insulation_mm = 50`;
- для сэндвича внешний диаметр хранится в `skus.outer_diameter_mm`.

## 7. Где живут правила совместимости

Правила совместимости не нужно прописывать текстом в каждой карточке товара.

Правила живут в БД:

```text
compatibility_rules
```

Поля:

```text
code
name
rule_type
applies_to_product_kind
conditions jsonb
result jsonb
severity = info / warning / error
message
is_active
```

Seed базовых правил:

```bash
python -m app.db.seed_compatibility_rules
```

API:

```text
GET  /api/v1/compatibility/rules
POST /api/v1/compatibility/check
```

Карточка товара получает рассчитанные `compatibility_messages` внутри каждого SKU.
Конфигуратор должен использовать те же правила, а не отдельную копию логики.

## 8. Как конфигуратор должен искать товары

Не по slug и не по названию.

Пример запроса логики:

```text
найти трубу 1000 мм:
  product_kind = труба
  contour = сэндвич
  diameter_mm = выбранный_диаметр
  insulation_mm = 50
  length_mm = 1000
```

Пример для отвода:

```text
найти отвод 90:
  product_kind = отвод
  contour = сэндвич или одностенный по зоне
  diameter_mm = выбранный_диаметр
  angle_deg = 90
```

## 9. Первый алгоритм комплекта MVP

Входные данные:

```text
source_type          # банная печь / камин / котел
diameter_mm          # диаметр патрубка
total_height_m       # общая высота
indoor_height_m      # теплый участок
outdoor_height_m     # холодный/уличный участок
roof_type            # скатная / плоская
route_type           # через кровлю / через стену
needs_cleanout       # нужна ревизия
```

Минимальный расчет:

1. Проверить `diameter_mm`.
2. Добавить стартовый одноконтурный элемент от источника, если схема это допускает.
3. Для теплого участка подобрать одноконтурные трубы нужной длины.
4. Перед проходом добавить переход на сэндвич.
5. Для прохода добавить проходной узел / разделку.
6. Для холодной/уличной части подобрать только сэндвич-трубы.
7. Добавить кровельную разделку.
8. Добавить оголовок/зонт/дефлектор.
9. Добавить крепеж по высоте и типу трассы.
10. Если есть ревизия/тройник — добавить заглушку/конденсатоотвод по типу узла.

## 10. Набор product_kind для правил

Используем такие значения:

```text
труба
отвод
тройник
четверник
шибер
ревизия
конденсатоотвод
заглушка
крепеж
оголовок
проходной_узел
```

Если новый товар не маппится в один из этих типов — он не должен участвовать в автоподборе до
ручной классификации.

## 11. Что пока нельзя автоматизировать без уточнений

Нужно уточнить у дымоходчиков:

- допустимую длину одноконтурного участка от печи;
- где именно обязателен сэндвич для банной печи;
- правила прохода деревянного перекрытия;
- сколько крепежа на метр вертикального участка;
- когда нужен тройник с ревизией;
- когда нужен конденсатоотвод;
- различия по газовому котлу / камину / твердотопливному котлу;
- допустимые марки стали под разные источники.

До уточнения эти пункты должны быть предупреждениями или ручной проверкой, а не молчаливой
автоматикой.
