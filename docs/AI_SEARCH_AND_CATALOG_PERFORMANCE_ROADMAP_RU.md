# Dimohod Trade: roadmap ускорения каталога и AI-search visibility

Дата начала: 2026-08-31  
Статус: в работе  
Владелец решения: Dimohod Trade

## 1. Цель

Сделать публичный каталог быстрым и стабильно доступным для покупателей, поисковых роботов и AI-поиска, а затем добавить безопасный навигационный слой `llms.txt`, улучшить индексируемый контур и измеримость.

Работа выполняется как надстройка над существующей системой. Текущая модель данных, правила выбора товара и публичные адреса не переписываются.

## 2. Неприкосновенные архитектурные контракты

- `Product` остаётся товарным семейством, `SKU` — конкретным вариантом.
- Не создаются отдельные индексируемые страницы для каждой комбинации параметров SKU.
- Существующие canonical URL и редиректы сохраняются.
- Query-параметры выбора исполнения не становятся индексируемыми страницами.
- SKU без эффективного описания или без применимого фото не возвращается в публичный каталог.
- Семейное фото применяется только к тем диаметрам и длинам, которые указаны в его области применения.
- Собственная фотография SKU имеет приоритет в рамках действующих правил медиа.
- Изменение кэша не должно задерживать публикацию цены, фото, описания или активности товара после сохранения в админке.
- Технические, монтажные и пожарные утверждения публикуются только из подтверждённых источников проекта.

## 3. Подтверждённая исходная проблема

После включения правила скрытия неполных SKU каталог стал заметно медленнее.

Текущий горячий путь:

1. Загружает активные `Product` вместе со всеми их `SKU`.
2. Для каждого SKU вызывает `public_sku_ready()`.
3. Для каждой проверки заново разбирает семейный JSON со списком медиа, диаметрами и длинами.
4. Фильтрует семейства и только после этого применяет пагинацию.
5. Повторяет часть проверок при сборке ответа каталога, фильтров, дерева категорий и sitemap.

Правило публикации корректное. Оптимизировать нужно способ его вычисления и объём загружаемых данных, а не ослаблять требования к фото и описанию.

- [x] Добавить поддержку IndexNow для явного списка новых и существенно изменённых публичных страниц.

Решения этапа:

- юридические страницы остаются доступными по ссылкам, но получают `noindex, follow` и исключаются из sitemap;
- `/raschet`, `/bystryy-raschet`, `/zamery` и `/solutions/banya/zamery` считаются рабочими зонами воронки, а не отдельными поисковыми посадочными;
- базовый `/configurator` остаётся индексируемой страницей инструмента, а его query-состояния сводятся к каноническому URL;
- категории и товарные страницы получают `lastModified` из фактического `updated_at` Product, SKU и Category;
- статические даты sitemap закреплены по последнему изменению соответствующих исходных файлов;
- ключ IndexNow задаётся только через `INDEXNOW_KEY`; без корректного ключа проверочный route отвечает `404`.

## 5. Порядок поставки

Каждый этап поставляется отдельно:

1. тест или замер, воспроизводящий проблему;
2. минимальное изменение;
3. профильные тесты;
4. полный доступный набор тестов;
5. production build для frontend-изменений;
6. замер до и после;
7. обновление этого roadmap;
8. только затем следующий этап.

Изменение URL, модели данных, правил совместимости или редакторского контента требует отдельного решения владельца.

## 6. Rollback

- P1: вернуть прямой вызов `public_sku_ready()` без изменения данных.
- P2: вернуть прежний запрос листинга; миграции БД на этом этапе не планируются.
- P3: отключить новый кэш и вернуть `no-store`.
- P4: вернуть предыдущие `robots.ts` и `sitemap.ts`.
- P5: удалить маршрут `/llms.txt`; остальные страницы продолжат работать.
- P6: удалить новый JSON-LD без изменения видимого интерфейса.
- P8: отключить отдельный лог и сохранить текущую конфигурацию приложения.

Ни один rollback не должен удалять товары, SKU, фотографии, заявки, сметы или пользовательские изменения.
