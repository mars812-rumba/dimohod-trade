# Удаление клиента со всеми сметами

Подготовлено 2026-11-18. Публикация — отдельной командой штатного native release.

## Интерфейс и границы

В общей карточке `/admin/customers` добавлено действие «Удалить клиента и сметы».
Оно относится ко **всем** заявкам этой карточки, а не только к последней смете.
Перед действием сервер показывает количество существующих заявок и файлов смет;
пользователь ставит отдельную галочку и нажимает «Подтвердить удаление».
Отмена и Escape ничего не удаляют. Изменение карточки или документов после
предпросмотра даёт 409 и требует нового подтверждения.

После успеха карточка исчезает из списка и поиска. Целиком переносятся папки
заявок: `lead.json`, `estimate.json`, заметки, вложения, PDF и версии смет.
Старые ссылки менеджера и PDF возвращают 404, пока запись не восстановлена.
Другие клиенты не меняются. PostgreSQL и схема БД не затрагиваются: CRM здесь
хранится в приватных файлах `MEDIA_STORAGE_DIR`, отдельно от Git и релизов.

Это обратимое удаление из рабочей CRM, **не безвозвратное уничтожение персональных
данных**. Уже отправленные письма, скачанные копии и резервные копии не удаляются.

## Корзина и восстановление

Архив создаётся в `<MEDIA_STORAGE_DIR>/leads/.trash/<deletion_id>/` с правами 0700:

```
manifest.json         # клиент, заявки, время и состояние операции
customer.json         # исходная общая карточка
leads/<lead_id>/      # исходные папки заявок целиком
```

Корзина находится внутри уже закрытого `/media/leads`: публичная раздача
не открывает ни документы, ни manifest. Автоочистки и окончательного удаления нет.
Штатный backup всего storage включает корзину; Git её не содержит.

Сразу после удаления показана кнопка «Восстановить клиента и сметы». В интерфейсе
она относится к последнему удалению и хранится до перезагрузки страницы. После
перезагрузки администратор может взять `deletion_id` из закрытого manifest и
вызвать API восстановления с административной авторизацией. Секретный токен
нельзя публиковать или вставлять в общедоступные URL.

Если после удаления пришла новая заявка с тем же контактом, восстановление
отказывается перезаписывать новую карточку (409). Старый архив и новая заявка
остаются на месте; объединение требует отдельного решения администратора.

## API и защита

- `GET /api/v1/admin/customers/{customer_id}/deletion-preview` возвращает
  `customer_id`, `version`, `lead_count`, `estimate_count`.
- `DELETE /api/v1/admin/customers/{customer_id}` принимает только
  `expected_version` и `confirmation: "delete_customer_with_estimates"`.
  Возвращает `status: deleted`, `customer_id`, `deletion_id`, `lead_count`.
- `POST /api/v1/admin/customers/trash/{deletion_id}/restore` возвращает
  `status: restored`, `customer_id`.

Все три маршрута требуют существующей административной cookie либо
`X-BOM-Admin-Token`. Одной ссылки/токена менеджера недостаточно. Успешные ответы
имеют `Cache-Control: no-store`; нет авторизации — 401, нет записи — 404,
конфликт/неоднозначные связи — 409, ошибка файлового хранилища — 503.

Состав удаления сверяется с индексом клиента и принадлежащими ему `lead.json`;
общие ссылки с другой карточкой блокируют операцию. ID строго проверяются,
символические ссылки не допускаются. Версия включает содержимое карточки и
пути/размеры/время изменения всех файлов заявок. Используется общая файловая
блокировка клиента, совместимая с добавлением смет и правкой имени. Поздняя
синхронизация старой заявки не возвращает её в новую карточку того же контакта.

Перенос выполняется переименованием на одном storage без копирования и удаления
файлов. При обычной ошибке предусмотрен обратный перенос. Это не транзакция
файловой системы: авария питания или повторный отказ диска во время отката могут
оставить `status: pending`. При таком состоянии сначала сверить manifest,
активные папки и архив, сохранить копию и восстановить недостающие записи под
контролем администратора; не перезаписывать существующие файлы и не чистить архив.

  предпросмотр, конфликт принадлежности, пропущенная индексом заявка, симлинки,

  подтверждение, ошибки, отмена и восстановление.
- Проверки браузером выполняются только на отдельном временном storage и тестовых
  клиентах, без удаления настоящих записей production.
  На 390 и 1280 px проверены подтверждение/отмена/Escape, конфликт после правки
  имени, отказ сети, 401, исчезновение карточки и ссылок, восстановление и

- Полный backend: 334 passed, 1 skipped; frontend: 414 passed. Изолированная
