# Обычные заявки в CRM — 2026-11-23

Проблема подтверждена по обращению `54cd75095c604d0893878b83ff58eeee`:
нижняя форма главной (`homepage-materials`) сохранила `lead.json` и отправила
письмо, но не создала индекс клиента. Ранее `create_lead` вызывал
`upsert_customer` только при наличии структурированной сметы.

Теперь обращения без сметы индексируются отдельно в `customer.inquiries`.
Новые заявки получают индекс до отправки письма. При чтении защищённого
списка клиентов `index_customer_inquiry` подхватывает старые активные
`leads/*/lead.json`. Повторная индексация ничего не дублирует и не переписывает
существующую карточку; исходные старые заявки остаются побайтно прежними.
Письма при индексации не отправляются, фиктивные сметы не создаются.

Идентичность клиента определяется существующим нормализованным контактом:
телефон/MAX/WhatsApp с одинаковым номером объединяют заявки и сметы.
Ручное имя менеджера сохраняется; старое обращение не заменяет более новое
автоматическое имя и не поднимает дату обновления до момента индексации.
Исторические email/Telegram-контакты также читаются, правила новых публичных
форм остаются ограниченными телефоном/MAX/WhatsApp.

В `/admin/customers` каждая обычная заявка показывает дату, исходный ID,
источник, комментарий и сохранённую конфигурацию/адрес страницы. Поиск
находит ID, источник и текст обращения. Заметки используют прежний закрытый
механизм с проверкой конкурирующих правок; добавлен путь
`/{customer_id}/inquiries/{lead_id}/notes` в admin API.

Вложения скачиваются через защищённый admin endpoint
`/api/v1/admin/customers/{customer_id}/inquiries/{lead_id}/attachment`:
проверяются сессия/токен, принадлежность заявки, имя и отсутствие symlink.
Ответ имеет `Cache-Control: no-store` и принудительное скачивание. Публичный
доступ к CRM/storage не добавляется.

Удаление и восстановление клиента охватывают `inquiries` и `estimates`.
Индексация использует тот же lock клиента и повторно проверяет существование
заявки после его получения. Удалённые записи в `leads/.trash` не сканируются
и не появляются заново из-за уже выполняющегося запроса списка.

Проверки:

- 72 backend-теста основной проверки: заявки, клиенты, заметки, имена,
  удаление/восстановление, быстрый расчёт. Дополнительно проверены старые
  Telegram/email/phone-only записи и удаление между чтением и взятием lock.
- 13 существующих frontend-тестов админки и удаления; production-сборка
  Next.js с TypeScript.
- `tools/check_customer_inquiries_browser.cjs`: старая заявка без сметы,
  смешанная карточка со сметой, поиск по ID, заметка с перезагрузкой,
  защищённое скачивание, удаление/восстановление, ширины 360/768/1440 px.
  Использован только `tests.customer_inquiries_preview` с синтетическими
  данными в `/tmp/dimohod-*`, без БД и SMTP.
- Локальная временная копия реальной заявки из письма найдена по её ID новым
  `list_customers`; исходный `lead.json` не изменился, дублей и сметы нет.

Миграция PostgreSQL и ручной перенос старых заявок не нужны. Production
и существующие записи на VPS в этой задаче не изменялись. После отдельного
native-релиза достаточно открыть или обновить список клиентов: индексация
старых обычных заявок выполнится автоматически.
