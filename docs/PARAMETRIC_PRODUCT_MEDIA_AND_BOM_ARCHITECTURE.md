# Параметрические карточки, SVG-геометрия и BOM

Обновлено: 2026-07-31

Статус: принятое архитектурное решение, реализация ещё не выполнена полностью.

Этот документ фиксирует общую архитектуру карточек параметрических товаров, размерных SVG-схем,
сцены конфигуратора и BOM для Dimohod Trade. Он дополняет:

- `PRODUCT_VARIANT_SEO_ARCHITECTURE.md`;
- `backend/configurator/CONFIGURATOR_RULES.md`;
- `docs/PROJECT_GUIDE_RU.md`.

## 1. Цель

Не создавать отдельные фотографии, рендеры и SVG-файлы для каждой комбинации диаметра, длины,
марки и толщины стали.

Вместо этого система разделяет:

```text
Product / geometry family  -> общий внешний вид и SVG-геометрия
SKU                        -> размеры, материал, артикул, цена и наличие
Configurator scene         -> расположение геометрий и точки соединения
BOM                        -> выбранные SKU, количество и причина выбора
```

Для нескольких тысяч SKU достаточно небольшого набора конструктивных SVG-семейств. На первом
этапе ожидается около 17 типов деталей, но фактических геометрий может быть меньше благодаря
повороту и отражению одного SVG.

## 2. Термины и границы владения данными

### Category

Навигационная категория каталога: трубы, отводы, тройники, оголовки и т. п. Текущая модель —
`Category` в `backend/app/modules/catalog/models.py`.

Категория не всегда подходит как владелец фотографии. В одной категории могут находиться
конструктивно разные изделия.

### Logical Product

Логическое изделие, объединяющее взаимозаменяемые по конструкции варианты. Текущая модель —
`Product` в `backend/app/modules/products/models.py`.

### Geometry family

Ключ конструктивной формы, например:

```text
sandwich-pipe
single-wall-pipe
elbow-90
tee-90
deflector-standard
deflector-large
```

Одна geometry family владеет:

- тремя общими фотографиями;
- одной базовой SVG-геометрией;
- точками соединения;
- правилами допустимого поворота/отражения;
- набором поддерживаемых размерных параметров.

Поэтому медиа следует привязывать к `geometry_family` или logical Product, а не автоматически ко
всей Category.

### SKU / Variant

Конкретная покупаемая позиция. Текущая модель — `SKU` в
`backend/app/modules/products/models.py`.

SKU хранит фактические размеры, артикул, материал, цену и наличие. Он не владеет копиями общих
фотографий и базового SVG.

## 3. Параметры размеров

Для первой версии используется единый контракт:

```ts
export type ProductDimensions = {
  L: number | null;
  D: number | null;
  d: number | null;
  S: number | null;
  insulation: number | null;
};
```

Значения:

- `L` — общая длина или высота изделия, мм;
- `D` — максимальный наружный диаметр, мм;
- `d` — внутренний рабочий/присоединительный диаметр, мм;
- `S` — толщина стали, мм.
- `insulation` — толщина изоляции сэндвич-элемента, мм.

Соответствие текущей модели SKU:

```text
L -> skus.length_mm
D -> skus.outer_diameter_mm
d -> skus.diameter_mm
S -> skus.wall_thickness_mm
insulation -> skus.insulation_mm
```

Для деталей, которым нужны дополнительные параметры, контракт расширяется именованными полями,
например `angle_deg` или `socket_length_mm`. Нельзя менять смысл `L/D/d/S/insulation` от
категории к категории без явного описания.

Марка стали, толщина изоляции и цена не создают новую SVG-геометрию, если конструкция изделия не
меняется.

## 4. Хранение медиа

Предлагаемая структура:

```text
storage/catalog/categories/
  deflector-standard/
    photo-1.jpg
    photo-2.jpg
    photo-3.jpg
    scheme.svg
  sandwich-pipe/
    photo-1.jpg
    photo-2.jpg
    photo-3.jpg
    scheme.svg
  elbow-90/
    photo-1.jpg
    photo-2.jpg
    photo-3.jpg
    scheme.svg
```

Имена файлов:

- только латиница;
- понятное назначение;
- без `IMG_1234`;
- один набор на geometry family.

Публичный URL в текущей инфраструктуре:

```text
/dimohod-media/catalog/categories/{geometry_family}/photo-1.jpg
/dimohod-media/catalog/categories/{geometry_family}/scheme.svg
```

Nginx уже публикует `/dimohod-media/` из каталога `storage/`; конфигурация находится вне
репозитория в `/etc/nginx/sites-enabled/sunny-rentals.online`.

### Роли фотографий

1. `photo-1.jpg` — основной общий вид;
2. `photo-2.jpg` — вид сверху или второй информативный ракурс;
3. `photo-3.jpg` — соединение, крепление или конструктивная деталь.

Нижний ракурс не обязателен. Он добавляется только тогда, когда показывает функциональный элемент,
которого не видно на других изображениях. Для диаметров одной конструктивной серии отдельные фото
не создаются.

## 5. Канонический SVG

`scheme.svg` хранит базовую векторную геометрию один раз на geometry family. Он не содержит
зашитых размеров конкретного SKU.

Базовая геометрия определяется только по главному фото реального изделия; существующий SVG не
является источником формы. Для дефлектора-конуса фронтальный технический контур состоит из:

1. широкого верхнего цилиндрического кожуха с двумя тонкими линиями отбортовки;
2. открытого воздушного зазора с видимым белым фоном;
3. отдельного короткого центрального внутреннего канала;
4. симметричного усечённого конуса с прямыми боковыми стенками;
5. отдельного короткого нижнего цилиндрического корпуса с линией отбортовки;
6. узкого центрального посадочного патрубка диаметра `d`.

Верхний кожух нельзя соединять с нижним корпусом сплошной внешней стенкой. Нижний переход нельзя
рисовать выпуклым, колоколообразным или похожим на вазу. Все элементы симметричны относительно
центральной вертикальной оси. Выносные линии `D/L/d/S` рендерятся отдельным информационным слоем.
Толщина утепления выводится отдельной текстовой строкой без точки и выносной линии.

Рекомендуемая структура SVG:

```xml
<svg viewBox="0 0 480 480" xmlns="http://www.w3.org/2000/svg">
  <symbol id="shape" viewBox="0 0 480 480">
    <!-- контуры изделия без конкретных цифр -->
  </symbol>
</svg>
```

React-компоненты используют одну и ту же геометрию через `<use>` и добавляют собственные слои:

```text
ProductShape       -> только контур изделия
DimensionScheme    -> контур + выносные линии + L/D/d/S
ConfiguratorPart   -> контур + точки стыковки, без размерных подписей
```

Размерная схема карточки всегда использует квадратный холст `480 x 480`. Компактная геометрия
детали в конфигураторе использует отдельный холст `200 x 200`: на нём нет размерных подписей,
но есть порты соединения.

Размерные значения не записываются обратно в файл и не создают новый SVG на диске.

## 6. Реестр геометрий

Код должен иметь единый реестр вместо условий по slug или названию товара:

```ts
type GeometryDefinition = {
  key: string;
  svgUrl: string;
  viewBox: string;
  supportedDimensions: Array<keyof ProductDimensions>;
  connectors: {
    top?: Point;
    bottom?: Point;
    left?: Point;
    right?: Point;
  };
  canRotate: boolean;
  canMirror: boolean;
};
```

Пример:

```ts
const geometryRegistry = {
  "sandwich-pipe": {
    svgUrl: "/dimohod-media/catalog/categories/sandwich-pipe/scheme.svg#shape",
    viewBox: "0 0 120 400",
    supportedDimensions: ["L", "D", "d", "S"],
    connectors: {
      top: { x: 60, y: 0 },
      bottom: { x: 60, y: 400 },
    },
    canRotate: true,
    canMirror: false,
  },
};
```

Горизонтальная труба не является отдельным изображением: используется та же геометрия с
поворотом на 90°. Левый и правый отводы по возможности строятся поворотом или отражением.

## 7. Компонент DimensionScheme

Целевой интерфейс:

```tsx
<DimensionScheme
  geometryFamily="deflector-standard"
  dimensions={{ L: 200, D: 115, d: 100, S: 1.5, insulation: 50 }}
  title="Дефлектор"
/>
```

Компонент:

1. получает описание геометрии из реестра;
2. рендерит базовый контур;
3. строит выносные линии;
4. подставляет значения в SVG `<text>`;
5. показывает толщину изоляции, марку и материал стали из выбранного SKU;
6. добавляет `<title>` и `<desc>` для доступности;
7. не является единственным местом, где опубликованы размеры.

Для SEO и доступности значения обязательно повторяются обычным HTML под схемой.

## 8. Карточка SKU

Карточка выбранного варианта состоит из:

```text
Галерея geometry family: 3 фото
Параметрическая DimensionScheme
HTML-таблица характеристик
Артикул, цена и наличие
Сообщения совместимости
Выбор соседних SKU
```

Таблица характеристик обязательно содержит:

- артикул;
- `L`, `D`, `d`, `S` с единицами;
- материал;
- марку стали;
- толщину стали;
- контур и изоляцию, если применимо.

Параметры на схеме не заменяют текстовые характеристики.

## 9. Alt, metadata и JSON-LD

Базовый alt:

```text
{Тип узла} Ø{D} мм, L={L} мм, D={D} мм, d={d} мм, S={S} мм
```

Пример:

```text
Дефлектор Ø115 мм, L=200 мм, D=115 мм, d=100 мм, S=1,5 мм
```

Title:

```text
{Тип узла} {D}×{d} мм, L={L} — купить | Дымоход Трейд
```

Description повторяет параметры естественным текстом и добавляет материал, назначение и условия
совместимости.

На SKU-странице публикуется `Product` JSON-LD с `sku`, `offers` и
`additionalProperty`. Каждый размер представлен как `PropertyValue`:

```json
{
  "@type": "PropertyValue",
  "name": "L",
  "value": 200,
  "unitCode": "MMT"
}
```

Аналогично публикуются `D`, `d` и `S`.

## 10. SVG-сцена конфигуратора

Текущий `ChimneyConfigurator` в
`apps/web/components/ChimneyConfigurator.tsx` уже строит одну SVG-сцену, но вставляет детали как
PNG через `<image>`. Целевое состояние — использовать `ConfiguratorPart` из общего реестра
геометрий.

Слои сцены:

```text
1. Фон: помещение, перекрытие, чердак, кровля, фасад
2. Детали дымохода: SVG-геометрии Product/SKU
3. Состояние: выделение, warning/error, выбранный элемент
4. Подписи сцены: зоны и общая высота
```

Размерные подписи `L/D/d/S` постоянно в сцене не показываются. На мобильном экране они создадут
визуальный шум. При выборе детали конфигуратор показывает отдельную HTML-карточку:

```text
Дефлектор
Арт. DT-DEF-300
L: 420 мм
D: 460 мм
d: 300 мм
S: 0,5 мм
```

## 11. Точки соединения и сборка сцены

Каждая геометрия объявляет порты:

```ts
type ConnectionPort = {
  id: "top" | "bottom" | "left" | "right";
  x: number;
  y: number;
  direction: "up" | "down" | "left" | "right";
  diameterRole: "inner" | "outer";
};
```

Алгоритм сцены совмещает выход предыдущей детали со входом следующей. Совместимость определяется
не SVG, а backend-правилами и полями SKU:

- рабочий `diameter_mm` должен совпадать;
- переход диаметра возможен только через явный переходник;
- наружные зоны требуют `contour = сэндвич`;
- крепёж использует наружный диаметр;
- ориентация и тип порта должны подходить маршруту.

SVG показывает результат, но не принимает решение о безопасности.

## 12. Масштабирование

Карточка товара и конфигуратор имеют разные задачи.

### DimensionScheme

Геометрия может масштабироваться пропорционально фактическим `L/D/d`. Выносные линии и текст
сохраняют читаемый экранный размер.

### Configurator scene

Нельзя использовать буквальный масштаб всех миллиметров: пятиметровая трасса не поместится на
мобильном экране. Используется визуальный масштаб с ограничениями:

- длины труб отражаются относительно друг друга;
- очень длинные участки сжимаются;
- соединительные элементы сохраняют минимальный читаемый размер;
- общая фактическая высота выводится текстом;
- BOM всегда рассчитывается по реальным размерам, а не по пикселям сцены.

## 13. BOM

SVG-сцена и BOM строятся из одного результата расчёта, но выполняют разные функции.

Целевая строка BOM:

```ts
type BomLine = {
  skuId: string;
  article: string;
  productName: string;
  productKind: string;
  geometryFamily: string;
  quantity: number;
  unitPriceRub: string | null;
  totalPriceRub: string | null;
  dimensions: ProductDimensions;
  selectionReason: string;
  zone: string;
  compatibilityMessages: CompatibilityMessage[];
};
```

BOM обязан содержать конкретный SKU. Нельзя хранить только `product_kind` или название детали,
потому что цена, артикул, размеры и материал принадлежат SKU.

Пример:

```text
Сэндвич-труба 115/200, 1000 мм, AISI 430 x 3
Стартовый элемент 115/200 x 1
Отвод 90 градусов 115/200 x 2
Дефлектор 115/200 x 1
```

## 14. Первый набор геометрий

Предварительный список:

1. источник тепла / печь как условный элемент сцены;
2. стартовый элемент;
3. одноконтурная труба;
4. сэндвич-труба;
5. переход одноконтурный -> сэндвич;
6. отвод 45 градусов;
7. отвод 90 градусов;
8. тройник;
9. ревизия;
10. конденсатоотвод;
11. заглушка;
12. проходной узел перекрытия;
13. проходной узел стены;
14. кровельная разделка для скатной кровли;
15. кровельная разделка для плоской кровли;
16. стеновой кронштейн;
17. оголовок / дефлектор.

Это список визуальных ролей. После инвентаризации часть ролей может использовать одну геометрию
с `rotate`, `mirror` или различным декоративным слоем.

## 15. Изменения модели данных

Текущих полей SKU уже достаточно для `L/D/d/S` большинства элементов. Не хватает устойчивой
привязки к geometry family и медиа.

Целевое минимальное расширение:

```text
products.geometry_family        varchar, nullable initially
products.media_key              varchar, nullable initially
```

Возможная нормализация на следующем этапе:

```text
geometry_families
  key
  name
  svg_path
  photo_paths jsonb
  connectors jsonb
  supported_dimensions jsonb
  renderer_version
```

На MVP допустим кодовый `geometryRegistry`, но Product должен получать ключ из backend, а не
определяться на frontend поиском слова в названии.

## 16. План реализации

1. Провести инвентаризацию реальных Product и свести их к geometry family.
2. Зафиксировать размерные обозначения каждой family.
3. Реализовать типы `ProductDimensions`, `ConnectionPort`, `GeometryDefinition`.
4. Создать `geometryRegistry`.
5. Перенести первые пять деталей из PNG в SVG:
   - сэндвич-труба;
   - стартовый элемент;
   - отвод 90 градусов;
   - переходник;
   - дефлектор.
6. Реализовать `ProductShape` и `DimensionScheme`.
7. Подключить SVG и HTML-характеристики к карточке SKU.
8. Реализовать metadata и JSON-LD выбранного SKU.
9. Заменить PNG в конфигураторе на `ConfiguratorPart`.
10. Подключить результат backend-расчёта и реальные BOM SKU.
11. Добавить визуальные и unit-тесты геометрии, соединений и metadata.

## 17. Критерии готовности

- один SVG-файл используется для всех размеров и марок стали одной geometry family;
- горизонтальная труба получается поворотом, а не отдельным рендером;
- три фотографии не дублируются по SKU;
- переключение SKU меняет цифры на схеме без создания нового файла;
- размеры присутствуют в обычном HTML;
- SKU-страница содержит корректные title, description и JSON-LD;
- конфигуратор использует ту же базовую геометрию, что карточка товара;
- сцена соединяет детали через объявленные порты;
- BOM содержит реальные `sku_id`, артикулы, количество, цены и причины выбора;
- правила совместимости выполняются backend-ом, а не SVG-компонентом;
- неизвестные размеры не угадываются и отправляются на ручную проверку.

## 18. Что не реализовано на дату документа

- `geometry_family` и `media_key` в PostgreSQL;
- таблица `geometry_families`;
- общий `geometryRegistry`;
- общие компоненты `ProductShape` и `ConfiguratorPart`;
- `DimensionScheme` для остальных geometry family (первая схема `deflector-cone` реализована в
  `apps/web/components/DimensionScheme.tsx` и подключена четвёртым элементом галереи);
- параметрические SVG всех деталей;
- SKU SEO route и JSON-LD;
- backend endpoint расчёта BOM;
- сохранение проектов конфигуратора.

Текущий frontend использует PNG-ассеты конфигуратора и временные проверки названий товаров.
Новая архитектура должна заменить эти временные решения постепенно, без дублирования данных.

## 19. Канонический промпт создания SVG-схем

При создании или редактировании параметрической схемы сначала использовать
[`PARAMETRIC_SVG_CREATION_PROMPT_RU.md`](./PARAMETRIC_SVG_CREATION_PROMPT_RU.md).
Документ фиксирует источник геометрии, холст 480×480, правила соединений,
динамические SKU-подписи, общий стиль и обязательные проверки. Общие новые правила
сначала добавляются в канонический промпт, затем применяются в реализации.
