- Sunny, Telegram-шлюз Codex и восстановительное окружение работают отдельно. Codex-бот работает с `/home/dimohod-recovery`, веткой `recovery/catalog-without-old-db` и native production pipeline. Старые скрипты деплоя на Beget запускать нельзя.

## Резервные копии

`dimohod-backup.timer`: ежедневно 03:20 UTC с задержкой до 20 минут; пропущенный запуск выполняется после включения сервера. Хранятся 14 завершённых копий, начальный дамп сохраняется отдельно.

```sh
systemctl start dimohod-backup.service
systemctl status dimohod-backup.service --no-pager
systemctl list-timers dimohod-backup.timer
```

Копии: `/home/dimohod-production-runtime/backups/<UTC-время>/`, права 0700/0600. Содержат database.dump, storage.tar.gz (включая CRM и вложения), source.tar.gz, production.env, systemd, конфигурацию Nginx, manifest.json и COMPLETE. Файл production.env содержит секреты: архив нельзя размещать в публичной папке или GitHub.

Первая копия проверена реальным восстановлением в отдельную временную базу; результат — `backup-restore-check.json`. Файлы также нужно регулярно скачивать на другой сервер или закрытый внешний носитель: текущие автоматические копии находятся на том же VPS и не защищают от его полной потери. Внешнее хранилище пока не подключено.

## Порядок переноса на другой сервер

1. Подготовить отдельного системного пользователя, PostgreSQL 16, Python 3.12, Node 22 и Nginx. Копировать текущий каталог release или source.tar.gz вместе с package-lock.json и backend/requirements-production.txt; установить зависимости. Утилита provision.py — первоначальная установка, не универсальный повторный мигратор.
2. Предварительно перенести storage и копию БД, не направляя туда пользователей. Создать отдельную роль приложения и базу, затем `pg_restore --no-owner --no-acl` с назначением владельца новой роли. Не запускать импорт исторических прайсов поверх восстановленной БД.
3. Создать закрытый production.env с новым DATABASE_URL и MEDIA_STORAGE_DIR; сохранить BOM_ADMIN_TOKEN, чтобы пароль и сессии админки продолжили работать. Указать прежний https://dimohod-trade.pro, secure cookies=true, выключенный SMTP до отдельной настройки.
4. Собрать Next.js с API_BASE_URL нового локального API, NEXT_PUBLIC_APP_URL и уведомлением, скопировать/адаптировать systemd и Nginx. Для новой системы сверить пути библиотек PostgreSQL и портов. Включить копирование резервных копий на внешний носитель.
5. Перед окончательным переключением остановить ТОЛЬКО dimohod-api и dimohod-web на старом VPS, сделать финальную копию БД и ВСЕГО storage. Это исключает потерю обращений между копированием файлов и базы. Sunny и Codex-бот не останавливать.
6. Перенести финальную копию, проверить каталог, расчёты, админку и приватность файлов на новом сервере. Переключить A-записи root/www, выпустить или безопасно перенести сертификат, проверить автообновление. На время распространения DNS прежний виртуальный хост можно проксировать на новый сервер, чтобы не иметь двух независимых записываемых копий CRM.
7. Сохранить прежний сервер и финальную копию до завершения проверки. При откате учитывать ВСЕ новые обращения на целевом сервере, а не просто переключать DNS назад.

## Если Beget вернёт старые данные

Сохранить текущие БД и storage. Старый дамп восстановить в ОТДЕЛЬНУЮ базу, проверить структуру и ревизию Alembic, при необходимости применить штатные миграции. Сверить SKU/цены, media-пути и правила. Отдельно запросить старое файловое storage: PostgreSQL не содержит всю файловую историю клиентов и КП. Новые записи текущего storage сохранять и объединять с проверкой конфликтов.

После проверки переключить DATABASE_URL и при необходимости MEDIA_STORAGE_DIR; ядро расчёта менять не требуется. RECOVERY-TEMP-позиции автоматически в старую БД не переносятся. Уведомление о восстановлении убрать из переменных сборки и пересобрать frontend только после подтверждения цен и полноты данных.

Не запускать provision.py/bootstrap_database.py/activate.py повторно поверх рабочего окружения: это установочные скрипты. Для обычной перезагрузки достаточно systemd.

## Генерация SEO через Anthropic

С 2026-11-05 генерация описаний `/admin/catalog` использует Anthropic Messages API,
модель `claude-sonnet-5-5`. Ключ `ANTHROPIC_API_KEY` и необязательное переопределение
`ANTHROPIC_SEO_MODEL` задаются в закрытом production.env. После смены ключа/модели
перезапустить только dimohod-api.service. OpenAI API для этого действия не используется.

Ответ ограничен JSON-схемой четырёх текстовых полей, проверяется локально и возвращается
редактору как черновик. Существующие пакеты подтверждённых фактов, предупреждения и
ручное сохранение сохраняются. При отсутствии средств или неверном ключе админка
показывает причину; неполный JSON/отказ модели не принимается за готовое описание.

### Доступ Anthropic через прежний VPS

С нового VPS в РФ Anthropic возвращает HTTP 403 Request not allowed даже
при действующем ключе; тот же ключ с прежнего VPS получает HTTP 200.
По согласованию с владельцем только SEO-запросы используют закрытый маршрут
через прежний VPS. Сайт, каталог, PostgreSQL, CRM, фотографии и PDF работают
на новом сервере независимо от этого маршрута.

На 157.228.120.191:

- `dimohod-anthropic-proxy.service`: Python CONNECT relay, пользователь
  dimohod-anthropic, только 127.0.0.1:18444, разрешён единственный адрес
  api.anthropic.com:443. Ключи и содержимое запросов не расшифровываются.
- `dimohod-anthropic-tunnel.service`: SSH reverse forward на
  root@168.113.191.165, только 127.0.0.1:18443 целевого сервера.
  Используется существующий deploy key; автозапуск и переподключение включены.
- Реализация relay и обе службы сохранены в deploy/native-runtime/.
  Для восстановления создать системного пользователя dimohod-anthropic,
  установить скрипт в runtime/anthropic-connect-proxy.py и unit-файлы
  в /etc/systemd/system; затем daemon-reload и enable --now обеих служб.

На 168.113.191.165 в private/production.env:
`ANTHROPIC_PROXY_URL="http://127.0.0.1:18443"`.
Настройка применяется только к клиенту генерации SEO, не к другим API.
HTTPS проверяется штатно до api.anthropic.com; прокси не получает открытый
API-ключ. Проверены запреты других хостов, других портов и внутренних адресов.

Если старый VPS недоступен, генерация SEO временно недоступна; остальные
функции приложения продолжают работать. Перед отключением старого VPS нужно
перенести этот маршрут на доступный для Anthropic сервер и обновить настройку.
Удаление ANTHROPIC_PROXY_URL возвращает прямое подключение, которое на текущем
российском IP не работает. Старые службы Дымоходов при этом запускать не нужно.
