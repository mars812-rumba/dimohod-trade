# Аудит URL-схемы карточек товара — 2026-08-06

## Что было до исправления

`Product` является товарным семейством, а `SKU` — конкретным исполнением. Однако публичные ссылки
смешивали эти уровни:

- страница открывалась через один Next.js route `/product/[slug]`;
- slug в пути относился к `Product`, но выбранный вариант передавался как `?sku=<UUID>`;
- каталог, рекомендации и клиентское переключение вариантов создавали такие ссылки;
- canonical и URL `Product`/`Offer` в JSON-LD могли содержать тот же идентификатор варианта;
- отдельные `robots.txt` и `sitemap.xml` в приложении отсутствовали;
- генератор семейного slug мог повторять тип изделия: `sendvich-truba-truba`.

Пример старой схемы:

```text
/product/sendvich-truba-truba?sku=92be0000-4b72-4b72-b722-02ab179ecd1f
```

Это создавало технически разные адреса для длины, толщины и марки стали внутри одного поискового
намерения и позволяло UUID попасть во внутренние ссылки и canonical.

## Принятая публичная схема

Индексируемая единица — `Product + диаметр`:

```text
/product/sendvich-truba-d100-200
/product/sendvich-truba-d115-215
/product/odnostennaya-truba-d115
```

Правила:

- `d100-200` означает внутренний/наружный диаметр конкретного семейства;
- длина, внутренняя и наружная марка стали, толщина и другие SKU-поля не входят в canonical URL;
- при переходе из отфильтрованного каталога конкретный SKU может временно передаваться по артикулу,
  например `/product/sendvich-truba-d100-200?sku=DT-SW50-...`;
- адрес с `sku` получает `noindex,follow` и canonical на чистый URL семейства с диаметром;
- старый `?sku=<UUID>` и legacy-path с UUID в конце перенаправляются на чистый URL;
- переключение исполнения в карточке удаляет технический параметр из адресной строки, а при смене
  диаметра обновляет человекочитаемый путь;
- API по-прежнему вправе использовать UUID внутри запросов и данных — запрет относится к публичному URL.

## Canonical, JSON-LD, robots и sitemap

- `<link rel="canonical">`, OpenGraph URL, `Product.url` и `Offer.url` теперь указывают на один чистый
  URL `Product + диаметр` без UUID и второстепенных характеристик.
- `robots.txt` разрешает обход публичных страниц, закрывает `/admin` и объявляет sitemap.
- `sitemap.xml` получает с backend уникальные активные пары `product_slug + diameter` и публикует
  только чистые адреса без query string и UUID.
- Query-страницы SKU не закрыты через `robots.txt`: роботу нужно разрешить их прочитать, чтобы увидеть
  `noindex` и canonical.

## Генерация и миграция slug

- Импорт и группировка больше не повторяют `product_kind`, если название уже начинается с него.
- Миграция `202608060001_normalize_public_product_slugs.py` исправляет уже сохранённые повторы и
  сохраняет прежний slug в `_seo_public_slug_previous`.
- Backend принимает сохранённый прежний slug как alias, после чего frontend перенаправляет на новый
  человекочитаемый адрес.
- При конфликте уникальности миграция оставляет существующий slug без изменения.

## Примеры до и после

| Сценарий | До | После |
|---|---|---|
| Труба 100/200, любой SKU | `/product/sendvich-truba-truba?sku=<UUID>` | `/product/sendvich-truba-d100-200` |
| Тот же диаметр, длина 500/1000 мм | отдельные query-URL варианта | один canonical `/product/sendvich-truba-d100-200` |
| Переход из фильтра по конкретной стали | `?sku=<UUID>` | временно `?sku=<артикул>`, `noindex`, canonical без query |
| Старый сохранённый URL с UUID | публично открывался как вариант | redirect на чистый URL диаметра |

## Проверка индексации

По исходному коду до исправления sitemap/robots не генерировались, поэтому гарантии исключения UUID
из sitemap не было. Поиск по коду подтвердил UUID-ссылки. Проверить фактический индекс поисковых
систем и ответы production `robots.txt`/`sitemap.xml` из текущего sandbox не удалось: внешний домен
не разрешался по DNS. После выкладки нужно проверить HTTP-ответы и Google Search Console отдельно.
