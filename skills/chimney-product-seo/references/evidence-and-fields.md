# Источники и структурированные поля

## Приоритет источников

Использовать в таком порядке:

1. Поля `Product` и выбранного `SKU` в БД.
2. `Product.extra_attributes.seo_knowledge`, заполненный и проверенный редактором.
3. Активные правила `compatibility_rules`, применимые к выбранному SKU.
4. Утверждённая техническая документация, явно указанная в `sourceNotes`.
5. Утверждённая база знаний проекта.

Название товара, slug, фото, предположение модели и неутверждённый внешний материал не являются доказательством технического утверждения.

## Минимальная схема без миграции

Хранить один объект на семействе в существующем JSONB `Product.extra_attributes`:

```json
{
  "seo_knowledge": {
    "purpose": [],
    "installationZones": [],
    "compatibleWith": [],
    "incompatibleWith": [],
    "installationVariants": [],
    "selectionRules": [],
    "installationWarnings": [],
    "fireSafety": [],
    "requiredInputData": [],
    "sourceNotes": [],
    "configuratorCta": {
      "text": "Подберите совместимые элементы и рассчитайте полный комплект дымохода в конфигураторе.",
      "href": "/#calculator"
    }
  }
}
```

Массивы содержат короткие самостоятельные подтверждённые утверждения. `sourceNotes` должен позволять редактору определить происхождение технических сведений; ссылка сама по себе не доказывает остальные поля.

## Разделение семейства и SKU

- Семейство: назначение, место в системе, общие зоны, допустимые сценарии и ограничения.
- SKU: артикул, d/D/L/S, утепление, материал, марка стали, угол, контур и иные фактические поля выбранного варианта.
- Не переносить значение одного SKU на всё семейство.
- Не превращать набор значений семейства в основной текст; использовать его только как краткий диапазон.

## Правила совместимости

Передавать генератору только активные правила, которые действительно применимы к контексту выбранного SKU. Сообщения правил использовать как совместимость или предупреждение. Считать их пожарными требованиями только при явной классификации/источнике.
